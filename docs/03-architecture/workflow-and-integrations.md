# Workflow and integration strategy

The FULCRUM workflow engine owns FCRM states, transitions, SLA timers for assessment work, assignments, escalations, and authorization. Jira owns general initiative/project execution workflow, assignees, task status, and collaboration. A Jira transition is context only and cannot advance a FULCRUM human gate or create a decision. AI tasks are asynchronous, retryable, idempotent, and cannot advance a human gate. Failed or low-confidence tasks create an escalation and preserve partial artifacts.

Integration priority: identity/RBAC and document/policy sources first; Jira Cloud OAuth 2.0 3LO for authoritative initiative context and engineering traceability; notifications and observability next; Confluence/SharePoint only where business value and approved access exist. The current implementation includes an authenticated, synthetic-only Jira sandbox for fixed-project search and explicitly confirmed test-account mutations. It does not synchronize Jira into FULCRUM or advance FULCRUM workflow. Jira design is documented in [Jira OAuth integration](jira-oauth-integration.md) and [Jira sandbox](jira-sandbox.md). Production adapters must add authorization, rate limits, retries, provenance, data handling, token revocation, reconciliation, durable token custody, and operational ownership.
